0. READ THIS FIRST - WHAT THE ZIP IS AND IS NOT
---------------------------------------------------------------------
* Amethyst 2.2.1 is a native-mod runtime for Minecraft Bedrock
  1.21.0.3 on WINDOWS (x86-64, MSVC, PE files, UWP/GDK). mod.json says
  platforms: "win-client". It builds with xmake + MSVC + SafetyHook.
* It contains NO binaries (no .dll/.so/.lib) - source only.
* So: none of its byte signatures or 0x... addresses work on Android
  (ARM64, ELF libminecraftpe.so). Do NOT copy them.
* What IS reusable (and valuable):
    A. The architecture (events, hook manager, importer, packs, UI).
    B. ~467 headers with real game class/function declarations:
       exact function names, parameter types, return types, and
       virtual-function indices (@vidx) for MC 1.21.0.3.
    C. A verified list of ~35 game functions that are hooked
       successfully in a shipping runtime (section 4).
    D. A clean model for the "--symbols index" (section 6).
* Biggest open question: does your LeviLauncher Android build use
  1.21.0.3? If not, names still mostly hold across versions, but
  vtable indices and signatures must be re-derived from YOUR
  libminecraftpe.so (build-id specific).

1. HOW AMETHYST'S PIECES WORK (and the converter equivalent)
---------------------------------------------------------------------
1.1 Importer (the "symbols" system)  <- most important idea
  * Game functions/variables are declared in C++ headers with the MC
    macro (dllimport) and an annotation comment:
        /// @sig {48 89 5C 24 ? 55 56 57 ...}    byte pattern, ? = wildcard
        /// @address {0x59EF9F8}                  fixed RVA for one build
        /// @vidx {035}                           virtual table slot
        /** @vtable */ / MC static uintptr_t $vtable_for_this;
        /// @symbols  or  /// @symbolgeneration  (file-level markers)
    A sig can be scoped: "{pattern, win-server}" (per-platform).
  * Build step (mod_build.lua): Amethyst.SymbolGenerator parses the
    headers with clang -> *.symbols.json; LibraryGenerator makes an
    import .lib; ModuleTweaker patches the mod binary so imports
    resolve at load time. At runtime the PEImporter reads the symbol
    records (V1 PEFunctionSymbol fields: IsDestructor, IsVirtual,
    VirtualIndex, VirtualTable, IsSignature, Signature, Address) and
    fills in the real addresses by sig-scan (libhat), address, or
    vtable lookup.
  * Result: mod code just writes  &Item::getAttackDamage  and calls
    game functions like normal C++ - no manual address plumbing.
  => For the converter: generate the same kind of table. Keep headers
     (or a JSON) as the single source of truth: class, method, params,
     kind {sig|address|virtual|vtable|dlsym}, per MC build-id.

1.2 HookManager / InlineHook
  * HOOK(Class, fn)   -> inline hook a normal function.
  * VHOOK(Class, fn, vtableFor) -> hook a virtual function by
    reading the vtable entry (GetVirtualFunctionOffset<fn>()).
  * Also supports hooking $constructor / $destructor pseudo-symbols
    (Minecraft::$constructor, ClientInstance::$constructor).
  * Hook pattern (this is exactly what a Mixin becomes):
        InlineHook<decltype(&Cls::fn)> _Cls_fn;       // trampoline
        R Cls_fn(Cls* self, Args...) {
            /* "HEAD" code */
            R r = _Cls_fn(self, args...);             // call original
            /* "RETURN" code */
            return r;
        }
        HOOK(Cls, fn);
  * Caveat they document: two mods hooking the same function via the
    raw absolute API conflict; use the shared hook API.
  * Mixin.hpp / Mixin.cpp in the zip are 7-byte stubs ("/// WIP").
    Amethyst has NO real mixin system - the transpiler idea is new
    territory, so the table in section 3 is the design to implement.
  * ANDROID NOTE: SafetyHook is x86-only. On ARM64 use whatever hook
    API the LeviLauncher template already exposes; otherwise Dobby,
    ShadowHook or And64InlineHook are the usual choices. (I haven't
    verified which the template uses - check before choosing.)

1.3 EventBus (decouple hooks from mod code)
  * One tiny typed bus: AddListener<Event>(fn), Invoke(event),
    ReverseInvoke(event); CancelableEvent has Cancel()/IsCanceled().
  * Runtime hooks fire events; mods only subscribe. Events present:
      Register*:  RegisterItemsEvent(ItemRegistry&, CreativeItemRegistry&)
                  RegisterBlocksEvent(BlockDefinitionGroup&)
                  InitBlockGraphicsEvent, InitBlockEntityRenderersEvent
      Game:       OnStartJoinGameEvent, OnRequestLeaveGameEvent,
                  UpdateEvent(Minecraft&) [per-tick],
                  OnLevelConstructedEvent, OnLevelDestroyedEvent
      Rendering:  BeforeRenderUIEvent/AfterRenderUIEvent
                  (ScreenView&, MinecraftUIRenderContext&),
                  BeforeRenderLevelEvent/AfterRenderLevelEvent
      Input:      RegisterInputsEvent, MouseInputEvent (cancelable)
      UI:         UIButtonHandleEvent
      Mod:        AddModEventListenersEvent, BeforeModShutdownEvent
  => For the converter: map Fabric/Forge events onto these (sec. 3).
     Native converted mods then compile against ONE small event API
     instead of raw hooks, so the hook set is written once.

1.4 Registering items/blocks (custom content logic)
  * VanillaItems::registerItems is hooked -> fires RegisterItemsEvent.
  * BlockDefinitionGroup::registerBlocks is hooked ->
    RegisterBlocksEvent (event fires BEFORE the original runs, so
    mod blocks exist before the group is finalized; items fire
    around registerItems - check src/hooks/shared/ItemRegistry.cpp).
  * CreativeItemRegistry (AmethystAPI/src/amethyst/game): mods call
    GetVanillaCategory(Construction/Nature/Equipment/Items/
    CommandOnly).AddCreativeItem(block). It queues items and the
    runtime flushes them from hooks on VanillaItems::_addXCategory,
    so the mod never fights creative-tab timing.
  => Lesson for the converter: registration order/timing is the
     classic failure; copy this queue-then-flush design.

1.5 Resource/behavior packs shipped by a mod
  * Mod folder layout (per mod, versioned):
      mods/<Name>@<ver>/mod.json
      mods/<Name>@<ver>/win-client/<mod>.dll
      mods/<Name>@<ver>/resource_packs/<pack>/manifest.json ...
      mods/<Name>@<ver>/behavior_packs/<pack>/manifest.json ...
  * PackManager.RegisterNewPack(mod, path, Resources|Behavior,
    priority) validates manifest.json (uuid + [x,y,z] version) and
    remembers it. Priorities Lowest..ExtremelyHigh.
  * Injection points (all hooked, all verified in 1.21.0.3):
      ResourcePackRepository::_initializePackSource  -> adds a
          DirectoryPackSource for each mod's resource_packs/behavior_packs
      VanillaGameModuleClient::initializeResourceStack (virtual)
      VanillaGameModuleServer::initializeBehaviorStack (virtual)
        -> addFromUUID({uuid, version}) on the pack stack
  => This is how a .levipack can carry textures, models, lang, item
     and block JSON, recipes, loot, animations with zero code.
     Check whether LeviLauncher already mounts packs from a mod
     folder; if not, these 3 hooks are the way.

1.6 UI
  * Two layers: (a) JSON UI in a resource pack (they author it as
    TSX via the Regolith-Generators deno lib -> ui/*.json), and
    (b) native C++ feeding it data:
      StartMenuScreenController::_registerBindings hook ->
        self->bindString(StringHash("#amethyst_version"), getter, enabled)
      JSON UI label then uses  text_binding "#amethyst_version".
      ScreenController::_handleButtonEvent hook -> UIButtonHandleEvent
        (buttons clicked in JSON UI reach native code).
      ScreenView::setupAndRender hook -> Before/AfterRenderUIEvent
        (immediate-mode drawing with MinecraftUIRenderContext).
  => This is the exact recipe for your Forge Menu / Better-Bedrock
     style Mods/Editor/Settings screens: JSON UI pack for layout +
     bindString for the mod list + button events for toggles.
     NinesliceHelper.hpp in amethyst/ui helps with 9-slice drawing.

1.7 Input
  * HOOKs: InputHandler::handleButtonEvent, MouseDevice::feed,
    VanillaClientInputMappingFactory::_addFullKeyboardGamePlayControls,
    _createScreenKeyboardAndMouseMapping, and a virtual hook on
    createInputMappingTemplates. InputManager registers custom
    actions (RegisterInputsEvent) -> custom keybinds.
  => Java KeyBinding mods map here.

1.8 Networking
  * MinecraftPackets::createPacket and
    ServerNetworkHandler::allowIncomingPacketId are hooked;
    CustomPacket.hpp / NetworkManager.cpp let a mod define its own
    packets (client<->server mods).

1.9 Mod loader / manifest model
  * mod.json (format_version 1.2.0): meta{uuid, namespace, name,
    version, author(s), is_runtime, platforms{win-client:{}},
    dependencies with {uuid|namespace, range, soft}}.
  * ModGraph resolves dependency order and rejects bad graphs;
    ModError enumerates failure kinds; ModInfo holds versioned name
    "<Name>@<ver>"; ModRepository scans folders; Version.hpp has
    semver ranges.
  => Good template for the .levipack manifest: uuid, namespace,
     version, per-platform entries (add android-arm64), soft/hard
     deps, mc-build compatibility list (see 6).

1.10 Misc useful utilities (amethyst/Memory.*)
  * SigScan with wildcards (libhat), SlideAddress(rva) = base+rva,
    GetEffectiveAddress(addr): decodes lea/call/jmp RIP-relative to
    the real target. Several sigs in headers start with E8 (call) -
    i.e. they anchor on a CALL SITE and resolve its target, which
    works when the callee's own prologue isn't unique.
    ARM64 equivalent: anchor on a BL imm26 and resolve it.
  * FindOffsetOfPointer(base, ptr, maxSize): finds a member offset by
    scanning an object for a known pointer - handy to discover field
    offsets at runtime when headers disagree with the build.
  * CompareVirtualTables(lhs, rhs, n): diffs two vtables - used to
    discover which slots a subclass overrides.
  * PatchManager.ApplyPatch(addr, bytes) with automatic restore on
    shutdown - for constant/byte patches (see @ModifyConstant below).

2. WHY THIS DIRECTLY ADDRESSES YOUR "CAN'T CONVERT" LIST
---------------------------------------------------------------------
Your four blockers and what the zip gives you for each:

 (a) MIXINS
     No ready mixin engine, but the HOOK pattern in 1.2 is a 1:1
     target for each Mixin annotation (table in section 3). The
     transpiler's job becomes:  Mixin target class+method  ->
     lookup in the symbols DB  ->  emit hook skeleton in the
     pattern above. If the symbol exists, it's a generated hook;
     if not, it becomes a TODO that names exactly what's missing.

 (b) MINECRAFT JAVA API CALLS
     Java names (Entity, PlayerEntity, ItemStack, World...) map to
     Bedrock classes (Actor, Player, ItemStack, Level/BlockSource).
     The headers give the exact Bedrock method names/params, so a
     mapping table "Fabric API method -> Bedrock method" can be
     written against real declarations (e.g. Actor::teleportTo,
     Mob::knockback, Player::attack, GameMode::destroyBlock).

 (c) CUSTOM ITEM/BLOCK LOGIC
     Split in two:
       - Data-driven part  -> emit behavior/resource pack JSON
         (item/block definitions, textures, lang, recipes) and ship
         it as a pack (1.5). No hook needed.
       - Code part (onUse, onBreak, tick, interactions) -> virtuals
         on Item / BlockLegacy / GameMode, listed with indices in
         the appendix (e.g. Item::getAttackDamage vidx 35,
         BlockLegacy::onFillBlock 53, GameMode::useItemOn).

 (d) GAMEPLAY / RENDERING CHANGES
     Gameplay: Actor::_hurt, Mob::knockback, Item::getAttackDamage,
     Player::getSpeed, GameMode::* (section 3 + appendix).
     Rendering: LevelRenderer::renderLevel (before/after),
     ScreenView::setupAndRender, BlockGraphics::initBlocks,
     BlockActorRenderDispatcher::initializeBlockEntityRenderers.
     Anything needing a different shader/pipeline is still manual.

3. MIXIN / JAVA-EVENT  ->  BEDROCK HOOK MAPPING TABLE
---------------------------------------------------------------------
3.1 Mixin annotation -> C++ hook shape
  @Inject  at HEAD            : code before calling _orig()
  @Inject  at RETURN          : code after _orig(); may read result
  @Inject  cancellable        : if (cancel) return default; (skip _orig)
  @Inject  at INVOKE/other    : usually a hook on the CALLEE instead
                                (or a mid-function patch - manual)
  @ModifyArg / @ModifyVariable: alter the parameter, then _orig(...)
  @ModifyReturnValue          : r = _orig(...); return f(r);
  @ModifyConstant             : byte patch via PatchManager (manual,
                                per-build) or hook the consumer
  @Redirect                   : hook the callee; filter by caller
  @Overwrite                  : hook, never call _orig
  @Accessor / @Invoker        : field offset / direct function ptr
                                from the symbols DB
  Mixin on a class (new fields): keep a side table keyed by object
                                pointer (std::unordered_map<void*,T>);
                                you cannot add fields to a game class.

3.2 Java concept -> known-good Bedrock hook (1.21.0.3 names)
  Mod init / tick ................ Minecraft::update (UpdateEvent),
                                   Actor::normalTick, GameMode::tick
  World load/unload .............. ClientInstance::onStartJoinGame,
                                   ClientInstance::requestLeaveGame,
                                   OnLevelConstructed/Destroyed
  Register items / blocks ........ VanillaItems::registerItems,
                                   BlockDefinitionGroup::registerBlocks
  Creative tab entries ........... VanillaItems::_add*Category hooks
  Attack damage of a weapon ...... Item::getAttackDamage (vidx 35),
                                   Item::getAttackDamageBonus (36)
  Attack another entity .......... GameMode::attack, Player::attack,
                                   Mob::attack (Actor::attack)
  Damage taken / cancel damage ... Actor::_hurt / Mob::_hurt (the
                                   float param is the damage; return
                                   false to cancel)
  Knockback ...................... Mob::knockback(Actor*, int, float x5)
  Death / kill ................... Mob::die, Mob::kill
  Player speed ................... Player::getSpeed
  Break block .................... GameMode::startDestroyBlock,
                                   continueDestroyBlock, destroyBlock
  Place block / use item on block  GameMode::buildBlock, useItemOn
  Use item ....................... GameMode::useItem, Item use virtuals
  Interact with entity ........... GameMode::interact
  Hover tooltip text ............. Item::appendFormattedHovertext
                                   (vtable hook, already proven)
  HUD / overlay drawing .......... ScreenView::setupAndRender
  World rendering ................ LevelRenderer::renderLevel
  Custom screens / buttons ....... StartMenuScreenController::
                                   _registerBindings,
                                   ScreenController::_handleButtonEvent
  Keybinds ....................... RegisterInputsEvent + InputHandler
  Custom packets ................. MinecraftPackets::createPacket
  Add textures/models/lang ....... pack injection (1.5)

3.3 Tier system the converter should use for every Java construct
  T0  Pure data -> pack JSON (items, blocks, recipes, loot, lang,
      textures, models, animations/animation controllers). Your
      "punch animation on hit" example lives here.
  T1  Known hook in the symbols DB -> generated C++ (this table).
  T2  Hook exists in headers but no signature for this build ->
      generated C++ + a precise "resolve me" entry in the symbols
      request list (class, method, param types, vidx).
  T3  No known target / mid-function / new field / shader ->
      TODO stub with the Java source embedded as a comment.
  Only T3 is left for hand-writing; T2 needs only a symbol lookup.

3.4 Things that may avoid native hooks entirely (NOT from the zip -
    general Bedrock knowledge; verify on your build)
  * Entity JSON overrides in a behavior pack can change many mob
    stats/attacks without code; custom-item components (damage,
    durability, food, etc.) handle new-item stats.
  * The Bedrock Script API (GameTest) may cover events like entity
    hurt / block break / item use for simple logic, if LeviLauncher
    can enable it. Worth testing before writing native hooks.
  * Vanilla item stat changes ("change attack damage" on a vanilla
    sword) generally cannot be done by packs -> needs the
    Item::getAttackDamage hook.

5. WINDOWS (MSVC) -> ANDROID (ARM64, Itanium ABI) PITFALLS
---------------------------------------------------------------------
Everything in the headers must be re-validated on Android:
 1. Name mangling: PE uses MSVC "?..." names, Android uses Itanium
    "_ZN...". If libminecraftpe.so keeps symbols in .dynsym you can
    dlsym; the packs you studied were stripped, so expect to need
    vtable/sig/address resolution instead.
 2. Vtable layout: Itanium vptr points past 2 header words
    (offset-to-top, typeinfo); the destructor takes TWO slots
    (complete + deleting), so every MSVC @vidx after 000 shifts +1
    on Android. MSVC groups overloaded virtuals together in
    reverse declaration order (you can see it in BlockLegacy:
    vidx 016 listed before 015); Itanium uses plain declaration
    order. Re-derive indices; don't trust @vidx blindly.
 3. Calling convention: x64 vs AAPCS64. `this` is x0 on ARM64;
    large struct returns use x8; small float aggregates (Vec3)
    come back in s0-s2 while MSVC returns them via hidden pointer.
    Hook signatures must match the real ABI.
 4. STL layout: MSVC std::string is 32 bytes, libc++ (Android) is
    24; std::function, unordered_map, shared_ptr internals differ
    too. Member OFFSETS in the Amethyst headers (which include such
    types) are wrong on Android. Field names/order are still good
    hints; recompute offsets (FindOffsetOfPointer trick, or
    disassembly of a getter).
 5. Instruction patterns: x64 byte sigs are meaningless on ARM64.
    ARM64 is fixed 4-byte instructions - build sigs from the first
    N instructions and MASK pc-relative bits (ADRP/ADD immediates,
    BL/B imm26, LDR literal, CBZ/TBZ offsets).
 6. Version drift: Amethyst targets 1.21.0.3 only. Key everything
    by (mc_version, ABI, ELF build-id) and refuse to hook on a
    mismatch instead of crashing.

6. PROPOSED "--symbols" INDEX (modelled on Amethyst's symbols.json)
---------------------------------------------------------------------
{
  "schema": 1,
  "mc_version": "<yours>", "abi": "arm64-v8a",
  "build_id": "<NT_GNU_BUILD_ID of libminecraftpe.so>",
  "functions": {
    "Item::getAttackDamage": {
      "kind": "virtual", "vtable": "Item", "index": 36,
      "ret": "int", "params": [], "const": true },
    "Minecraft::update": {
      "kind": "sig", "sig": "FD 7B ?? A9 ...", "anchor": "none" },
    "ScreenView::setupAndRender": {
      "kind": "sig", "sig": "...", "anchor": "bl_target" },
    "ClientInstance::onStartJoinGame": {
      "kind": "address", "rva": "0x..." }
  },
  "vtables": { "Item": { "rva": "0x...", "via": "rtti" } },
  "offsets": { "Actor::mLevel": "0x..." }
}
Resolution order at load: dlsym -> vtable(RTTI)+index -> sig ->
rva, then self-check (e.g. function prologue looks sane, sig unique).
If RTTI type names exist in the .so (check with `strings | grep
-i "N.*ItemE"`), vtables can be found even when stripped: locate the
typeinfo-name string -> typeinfo object -> vtable that references it.
I have not confirmed the Android build keeps RTTI; that's a quick
check on your .so.
